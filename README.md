# webpin

**Point at what's wrong on a web page, and get back the source line that needs editing.**

webpin serves your local web project, injects a small overlay into every HTML page it
sends, and lets you click on the rendered page to leave a note, rewrite a piece of text,
draw a box around a region, or tweak spacing and colors. Every instruction is stored
together with **the file and line in your source that produced it** — not the generated
HTML you were looking at.

You then hand the collected notes to an AI coding agent (or fix them yourself):

```bash
cd ~/projects/my-site
webpin              # click around in the browser, leave notes
webpin notes        # see what you collected, with source candidates
```

```
* 3 [comment] /portfolio/
    this heading sits too close to the image above
    text: Works
    at:   main > section:nth-of-type(2) > h2
    src:  portfolio/content.js:118  (テキスト一致)
+ 4 [edit] /lab/
    「Experiments」→「Lab notes」
    text: Experiments
    at:   main > h1
    適用: lab/lab.json:12
```

(`*` is an open note, `+` is one webpin already applied to your source. webpin's own
generated text is Japanese — see [Known limitations](#known-limitations).)

## Why this exists

Two problems, both of which show up as soon as you build a site with an AI assistant:

1. **Describing a location in words is expensive.** "The third paragraph, second half" /
   "the gap under the Works heading" — you have to re-specify the same place in prose
   every single time you want a change.
2. **What you see is often not what you edit.** If your site is generated by a build
   script, the visible HTML is an output artifact. Editing it directly gets your change
   wiped on the next build. The real source might be a `content.js`, a `translations.js`,
   a `*.json`, or a Markdown file — and you have to remember which.

webpin collapses both into one gesture: click the thing, say what you want, and the note
is recorded with the resolved source location attached.

## Requirements

| | |
|---|---|
| **Node.js 18+** | 20+ recommended. No dependencies — there is no `package.json` and **no `npm install` step**. Everything is the Node standard library, including the WebSocket client. |
| **macOS** | This is what webpin is built and tested on. It launches Chrome from `/Applications/Google Chrome.app`. See [Other platforms](#other-platforms) below. |
| **Google Chrome** | Only needed for region screenshots (webpin talks to it over the DevTools Protocol). Everything else works in any browser. |
| **PHP** *(optional)* | Only if your project has `.php` pages you want to render locally. If `php` isn't on your `PATH`, webpin says so and serves everything else normally. |
| **Git** *(optional)* | webpin walks up from your working directory to the nearest `.git` directory to decide what "the project" is. Without one, it just uses the directory you gave it. |

## Install

webpin runs directly from a checkout — there is nothing to build.

**1. Clone it somewhere permanent** (the symlink in step 2 points back into this
directory, so don't clone it into a temp folder):

```bash
git clone https://github.com/YoshitoSuzuki/webpin.git ~/tools/webpin
```

**2. Put `webpin` on your `PATH`.** Symlink the launcher into a directory your shell
already searches — `~/bin` and `/usr/local/bin` are the usual choices:

```bash
mkdir -p ~/bin
ln -s ~/tools/webpin/bin/webpin ~/bin/webpin
```

If `~/bin` isn't on your `PATH` yet, add it to your shell config (`~/.zshrc` for the
macOS default shell) and open a new terminal:

```bash
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.zshrc
```

**3. Verify:**

```bash
webpin --help
```

You should see the usage text. If you get `command not found`, your `PATH` change hasn't
been picked up — open a new terminal, or run `source ~/.zshrc`. If you get
`permission denied`, restore the executable bit with
`chmod +x ~/tools/webpin/bin/webpin`.

**To update later:** `git -C ~/tools/webpin pull`. The symlink keeps working.

**To uninstall:** `rm ~/bin/webpin`, delete the clone, and optionally
`rm -rf ~/.cache/webpin` (that's where your notes and screenshots live).

### Other platforms

The core — serving, the overlay, notes, source lookup, text rewriting — is plain Node and
works anywhere. Two macOS-specific pieces:

- **Launching the browser.** webpin spawns Chrome by absolute macOS path, falling back to
  the macOS `open` command. On Linux/Windows, start webpin with `--no-open` and open the
  printed URL yourself.
- **Region screenshots.** These need Chrome reachable over the DevTools Protocol on
  **`<port> + 2`**. To get them elsewhere, launch Chrome yourself with a throwaway profile:

  ```bash
  google-chrome --remote-debugging-port=<port+2> --user-data-dir=/tmp/webpin-chrome <url>
  ```

  Without that connection, region notes are still recorded — just without the image.

## Quick start

```bash
cd ~/projects/my-site   # any directory containing a web project
webpin
```

webpin prints the URL it's serving on and opens Chrome:

```
http://127.0.0.1:51281/  (/Users/you/projects/my-site)
```

- **The port is derived from the project path**, so a given project always gets the same
  URL, restart after restart. Override it with `--port 8080` if you need to.
- Chrome opens with a **dedicated profile** at `~/.cache/webpin/chrome`. This isn't
  optional: since Chrome 136, remote debugging is refused on your default profile, and
  screenshots depend on it. Your normal Chrome windows, profile and logins are untouched.
- **Editing a file reloads the page.** webpin watches the project directory and pushes a
  reload over Server-Sent Events.
- **Nothing is ever written into your project** except the text rewrites you explicitly
  make in the browser. The overlay is injected into the response, not into your files.
- **Stop with `Ctrl-C`.** Any `php -S` webpin started stops with it.

### Command-line options

```bash
webpin                       # serve the current project
webpin ~/projects/other      # serve a specific directory
webpin --port 8080           # pin the port
webpin --no-open             # don't launch a browser
webpin --live https://example.com   # borrow production for PHP pages (remembered)
webpin --local               # stop borrowing production
```

## The four modes

The toolbar sits in the bottom-right corner of every page. Click a mode to enter it;
click it again, or press `Esc`, to leave. **The overlay UI is in Japanese** — the labels
are given below.

### 注釈 — Comment

Hover to outline an element, click it, type a comment, press `追加` (add) or `Cmd+Enter`.
A numbered pin stays on the page. The note is saved with the element's CSS selector, its
text, and the ranked source candidates.

### 文字 — Text

Click a piece of text to edit it in place. `Enter` commits, `Esc` cancels. Only the
individual **text node** you clicked becomes editable, which is what lets a paragraph
containing `<br>` or `<strong>` still be matched against your source.

If the edit resolves unambiguously to exactly one non-generated source location, **webpin
rewrites the file for you**, re-runs `build.js` if there is one in that directory, and
reloads the page. The change is listed as `+` (applied) in `webpin notes` so you can
review it. Otherwise the edit is kept as an instruction for the agent to carry out.

webpin rewrites a file only when **all** of these hold — one miss and it becomes a note:

1. exactly one non-generated source candidate,
2. exactly one occurrence within that file,
3. the string is long enough (8+ ASCII characters, or 4+ Japanese characters),
4. the match sits in a plain string — no tags in the middle for HTML/PHP, a single
   quoted literal with no escapes or `${}` for JS/JSON.

Two deliberate exceptions: **deleting all the text never auto-applies** (removing an
element and leaving it empty are different intentions, so it becomes a note), and on
pages using `data-i18n`, only the language you're looking at is edited — the other
language becomes a "re-translate this" note rather than being machine-overwritten.

### 範囲 — Region

Press `範囲`, then drag a rectangle. A comment box appears where you released the mouse;
write and press `追加` (or `Cmd+Enter`). The rectangle is captured as a **screenshot of
the tab as it actually is** — current scroll position, open dialogs, scroll-triggered
animations already applied. Rectangles smaller than 8×8 px are ignored so a stray click
doesn't create one.

### 見た目 — Appearance

Click an element to get inputs for font size, padding, margin, color and background.
Changes preview live on the page. `記録` (record) saves the before/after values as a
note; `戻す` (revert) throws them away.

**This never writes CSS automatically.** Which file, which rule, and whether it belongs
inside a media query are judgment calls, so they're left to whoever applies the note.

### 一覧 — List

The pending notes. `×` deletes one. The number on the button is the open count.

## Reading and clearing notes

These work **whether or not the server is running** — they read the store directly.

```bash
webpin notes                 # open (*) and applied (+) notes
webpin notes --json          # machine-readable: absolute paths to sources and screenshots
webpin notes --all           # include resolved (-) notes
webpin show 3                # one note, as JSON
webpin done 3 --note "shortened the copy"
webpin clear                 # discard resolved notes
```

Status markers: `*` open · `+` webpin already rewrote the source, awaiting review ·
`-` resolved.

Each note carries: `kind` (`comment` / `edit` / `delete` / `translate` / `range` /
`style`), `page`, `selector`, `text`, `candidates` (ranked `file` / `line` / `why` /
`generated`), plus `applied` for auto-applied edits, `style` for appearance changes, and
`shotPath` for region screenshots.

## Using it with an AI agent

`webpin notes --json` is the handoff. Point your agent at it:

> Run `webpin notes --json` in this project and fix everything listed. Start from
> `candidates`; skip any candidate with `generated: true` — it's build output and the
> change would be lost on the next build. Open `shotPath` images to see region notes.
> Re-run `node build.js` in the relevant directory when you touch a build input. Mark each
> one finished with `webpin done <id>`.

In [Claude Code](https://claude.com/claude-code), the author keeps this as a skill at
`~/.claude/skills/web-review/SKILL.md`, invoked with `/web-review`. The rules that matter
if you write your own:

- **Start from `candidates`, and never edit a `generated: true` file** — use the source
  candidate with the same content instead.
- **`status: applied` means webpin already made the change.** Check it with `git diff`,
  then just mark it done. Any needed build has already run.
- **`kind: delete` is not "write an empty string."** Decide whether the element, key, or
  list item should go away entirely.
- **`kind: style` values are a starting point,** not text to paste into CSS.

## PHP pages

If `php` is available, webpin starts `php -S` on **`<port> + 1`** and proxies `.php`
requests to it, so PHP pages render locally and can be annotated like any other page.

Pages that need a database or a login usually can't run locally at all. For those,
webpin can borrow the responses from your live site:

```bash
webpin --live https://example.com
```

- **Remembered per project** (in `~/.cache/webpin/<project>/config.json`), so plain
  `webpin` keeps using it afterwards. Turn it off with `webpin --local`.
- Only requests that resolve to `.php`, **and files that don't exist locally**, go to
  production. Local CSS/JS/images are served from disk — so you see the real HTML while
  your local stylesheet edits apply immediately.
- **Logging in works.** Session cookies are rewritten to stick to localhost.
- Source lookup is unchanged: notes still resolve to files in your repo.

Two things to keep in mind while live:

- **You are looking at production.** Clicking a button that writes to the database
  writes to the real database.
- **Text edits change your source but not the screen**, because the HTML came from
  production. Confirm via the toast and the `+` marker in `webpin notes`; the visible
  change comes after you deploy.

## Where webpin puts things

Everything lives outside your repository, so nothing leaks into a published site:

| | |
|---|---|
| Notes | `~/.cache/webpin/<project>-<hash>/notes.jsonl` |
| Screenshots | `~/.cache/webpin/<project>-<hash>/shots/*.png` |
| Per-project config | `~/.cache/webpin/<project>-<hash>/config.json` |
| Chrome profile | `~/.cache/webpin/chrome` |

`notes.jsonl` is append-only and folded into current state on read, so the server and the
CLI can write at the same time without corrupting it.

Ports used, all derived from the project path: **`port`** (webpin), **`port + 1`**
(`php -S`), **`port + 2`** (Chrome DevTools Protocol).

## How the source lookup works

Short version — the full explanation is in [docs/architecture.md](docs/architecture.md):

1. **Take the text node under the cursor**, not the element's `textContent`, so markup
   inside a paragraph doesn't break the match.
2. **Collect candidates.** With a `data-i18n` attribute, look the key up directly and
   determine which language block it's in. Otherwise full-text search the project's
   `.html/.php/.js/.json/.md/.css`, tolerating differences in whitespace and HTML entities.
3. **Detect build output.** A `.html` file under a directory containing `build.js` and at
   least one `template_*.html`, which is not itself a `template_*.html`, is treated as
   generated. Such candidates are kept but ranked last — knowing the string also appears
   there is still useful.
4. **Rank.** `*.json` / `*.md` > `*.js` > `template_*.html` > plain `.html` > `.php` >
   `.css` > generated output, plus a bonus for path proximity to the page you're viewing.

## Troubleshooting

**`command not found: webpin`** — `~/bin` isn't on your `PATH`, or the shell hasn't
reloaded. See [Install](#install) step 2.

**Nothing opens, but the server started.** Another Chrome process is already holding the
`~/.cache/webpin/chrome` profile, so Chrome handed it the URL instead of opening a
window — and if that process is headless or shutting down, you see nothing. The server is
fine; you can paste the printed URL into any browser. To fix it properly:

```bash
ps aux | grep '[G]oogle Chrome' | grep 'cache/webpin/chrome'
pkill -f "user-data-dir=$HOME/.cache/webpin/chrome"
```

Then run `webpin` again.

**Region screenshots aren't saved.** webpin couldn't reach Chrome over the DevTools
Protocol — most often because the page is open in a browser webpin didn't launch. The
note is still recorded, with the rectangle coordinates and the elements inside it.

**`php が無いので .php は表示できません`** ("php not found, `.php` can't be rendered") —
install PHP, or use `--live` if the page needs a database anyway.

**A `.php` page returns 500.** It probably needs a database or a config file that isn't in
the repository. Layout review still works; for the real thing use `--live`.

**Text edits don't auto-apply.** That's by design whenever the target is ambiguous — check
`webpin notes` and you'll find it recorded as an instruction, along with the reason.

**Pages don't reload on save.** Recursive `fs.watch` isn't available everywhere (on Linux
it needs Node 20+). webpin degrades silently; reload manually.

## Known limitations

- Pages that depend on a database or session can't run locally — `--live` is the
  workaround, not a fix.
- Screenshots only work in the Chrome tab webpin opened.
- Strings assembled inside `build.js` itself (rather than read from a source file) resolve
  to zero candidates. They're still recorded as notes for a human or agent to trace.
- Automatic CSS changes are out of scope, on purpose.
- Overlay UI and CLI output are in Japanese; the docs under `docs/` are Japanese as well.

## Project layout

```
bin/webpin        argument parsing, subcommands, server + Chrome launch
lib/project.js    git-root detection, path hashing, port derivation, cache paths
lib/server.js     static serving, PHP proxy, overlay injection, SSE, /__webpin/* API
lib/live.js       forwarding to a production origin (DB/login-backed PHP pages)
lib/resolve.js    the source lookup: text search, build-output detection, ranking
lib/apply.js      auto-rewrite eligibility, context-aware re-escaping, build.js re-run
lib/store.js      append-only JSONL note store
lib/cdp.js        minimal WebSocket client + Chrome DevTools Protocol (~130 lines)
lib/shot.js       region screenshots
web/overlay.js    the entire browser-side UI (Shadow DOM, CSS inlined)
```
